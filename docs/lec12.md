# 第12回　コンパイル


## 到達目標

- ソース・ヘッダ・オブジェクト・実行ファイルの役割を説明できる．
- 複数のCファイルを1つの実行ファイルにまとめられる．
- 宣言と定義，静的ライブラリと動的ライブラリを区別できる．
- ヘッダの依存関係を整理し，構造体を使うプログラムも分割できる．
- ビルド失敗を前処理・コンパイル・リンクのどの段階かに分けて調べられる．

## 今回の見通し

第11回では，関連するデータを構造体にまとめました．今回は，関連する**型と関数をファイルにまとめる**方法を学びます．1つのファイルが長くなると，「どこに何があるか」が分かりにくくなり，同じ処理を別のプログラムで再利用するのも大変です．計算の仕組みと，その使い方を分けることから始めます．

最初は計算関数を3ファイルに分け，次にベクトルと行列を5ファイルに分けます．最後に，複数のプログラムから使えるライブラリへつなげます．ファイルを増やすこと自体が目的ではありません．「利用者が知る必要のある情報」と「実装の都合」を区別することが目的です．

今回も操作はVisual Studio内で行います．第1回の空プロジェクト，C17，Cとしてコンパイル，警告レベル4の設定を使います．これまでと異なり，**1つのプロジェクトに複数の`.c`を入れる**課題があります．ただし，実行ファイルを作るプロジェクトの`main`は1つです．


## 1　ビルドを分解する

第1回ではビルドを1回の操作として実行しました．内部では，インクルードなどを処理する**前処理**，Cのコードを機械語のオブジェクトへ変換する**コンパイル**，各部分を結び付ける**リンク**が行われます．コンパイラ内部でアセンブリ生成・アセンブルが別段階になることもあります．

~~~text
main.c + calc.h → 前処理・コンパイル → main.obj ┐
                                               ├→ リンク → アプリ.exe
calc.c + calc.h → 前処理・コンパイル → calc.obj ┘
                                    標準ライブラリも利用
~~~

`main.obj`には`add`を呼びたいという情報があり，`calc.obj`には`add`の実装があります．リンカが結び付けます．関数名の綴りが違ったり，実装のファイルがビルドされなかったりすると，リンク時に解決できません．

### 1.1　各段階で何が分かるか

| 段階 | 入力と主な仕事 | 典型的な問題 |
| --- | --- | --- |
| 前処理 | `#include`で取り込み，`#define`で置換し，条件付き部分を選ぶ | ヘッダが見つからない，条件の閉じ忘れ |
| コンパイル | 前処理後のコードを解析し，型を検査してオブジェクトを作る | セミコロン不足，未宣言の名前，型の不一致 |
| リンク | オブジェクトやライブラリ中の定義を結び付ける | 必要な定義がない，同じ定義が複数ある |
| 読み込み・実行 | 実行ファイルを読み込み，プログラムを動かす | 必要なDLLがない，入力に対する処理が誤っている |

オブジェクトには機械語だけでなく，関数や変数の名前，後で確定する参照先などの情報も入ります．`main.obj`ができたことは，`calc.obj`が見つかったことや，全体を実行できることを意味しません．

別の環境の資料ではオブジェクトが`.o`，Windows/MSVCでは通常`.obj`です．役割は対応しますが，ファイル形式や呼び出し規約が異なることもあるため，拡張子を変更して使い回せるわけではありません．

### 1.2　翻訳単位とビルドの単位

1つの`.c`にヘッダを取り込み，前処理を終えたものを**翻訳単位**と呼びます．`main.c`と`calc.c`は別々の翻訳単位です．`main.c`を処理するとき，コンパイラが自動的に隣の`calc.c`まで探して読んでくれるわけではありません．

通常のビルドは，変更されたファイルやその影響を受けるファイルだけを再処理します．`calc.c`の本体だけを変更した場合，主に`calc.c`の再コンパイルとリンクが必要です．`calc.h`を変更した場合は，それを取り込む`main.c`と`calc.c`の両方が影響を受けます．リビルドは対象の生成物を作り直す操作です．

!!! warning "実行できたかではなく，今回のビルドに成功したかを確認する"

    前回成功した`.exe`が残っていることがあります．ビルドに失敗した後で古い`.exe`を動かしても，修正を確認したことにはなりません．出力ウィンドウで成功・失敗を確認し，失敗時に以前の実行ファイルを起動する案内が出たら実行しません．

## 2　宣言と定義

**宣言**は名前と型を知らせ，**定義**は関数本体や変数の領域を与えます．関数の宣言はヘッダへ，定義は原則1つの`.c`へ置きます．同じ関数を複数の`.c`で定義すると重複の原因になります．

`#include "calc.h"` は前処理でヘッダの内容を取り込みます．ライブラリの実装をリンクする操作ではありません．`#include "calc.c"` で実装ファイルを取り込む方式にもせず，各`.c`を別々にコンパイルします．

### 2.1　関数の使い方を先に知らせる

~~~c
double add(double a, double b);  /* 宣言：末尾は ; */
~~~

この宣言から，`add`は`double`を2つ受け取り，`double`を返すと分かります．呼び出し側は，足し算の実装を見なくても引数と戻り値を扱えます．宣言の引数名は説明用であり，定義と同じ名前でなくてもかまいませんが，型は一致させます．

~~~c
double add(double a, double b)  /* 定義：関数本体がある */
{
    return a + b;
}
~~~

引数のない関数はC17では`void show(void);`のように書きます．`void show();`は「引数がない」という厳密な指定ではありません．プロトタイプを共有して，誤った呼び出しをコンパイル時に発見できる形にしましょう．

### 2.2　ヘッダに何を書くか

| ヘッダに置くもの | 実装の`.c`に置くもの |
| --- | --- |
| 外部から使う関数の宣言 | 関数の本体 |
| 外部から使う構造体の定義・型の別名 | 内部だけで使う型や補助関数 |
| 必要な定数マクロ | 計算手順や作業用の変数 |
| 必要なら共有変数の`extern`宣言 | 共有変数の定義を1か所だけ |

これは今回扱う通常の外部関数の分け方です．ヘッダに関数本体を書き，複数の`.c`から取り込むと，同じ外部関数の定義を複数のオブジェクトに作ってしまいます．また，呼び出し側と実装側に宣言を手書きで複製すると，変更時に片方だけ直す事故が起きます．**共通のヘッダを両方から読む**形にします．

`#include <stdio.h>`は処理系が提供するヘッダ，`#include "calc.h"`は自作ヘッダに用いる表記です．具体的な検索順序は処理系と設定に依存します．どちらの記法も「宣言を読む」ためのものであり，`.c`をビルド対象に追加する操作とは別です．

## 3　3ファイルの例

~~~c title="calc.h" linenums="1"
--8<-- "sample/12/calc.h"
~~~

`#ifndef`から`#endif`は**インクルードガード**です．同じ翻訳単位（前処理後の1つのソース）でヘッダの内容を重ねて取り込むのを防ぎます．別々の`.c`に同じ関数定義を入れたときの重複を防ぐ仕組みではありません．

~~~c title="calc.c" linenums="1"
--8<-- "sample/12/calc.c"
~~~

実装側も自分のヘッダを読み，宣言と定義の型の不一致を検出しやすくします．

~~~c title="main.c" linenums="1"
--8<-- "sample/12/main.c"
~~~

[`calc.h`](sample/12/calc.h){ download } ／ [`calc.c`](sample/12/calc.c){ download } ／ [`main.c`](sample/12/main.c){ download }

結果は `add=3.5` と `multiply=3.0` です．

### 3.1　1つの呼び出しを追跡する

`add(1.5, 2.0)`を例にします．`main.c`は`calc.h`から宣言を読み，2つの`double`を渡して`double`を受け取るコードになります．`calc.c`は同じ宣言を読み，`add`の本体をコンパイルします．リンクによって呼び出しと定義が結び付き，実行時に3.5が返ります．

`calc.c`の先頭でも`calc.h`を読むのは，利用者のためだけではありません．実装をうっかり`int add(int a, int b)`に変えると，ヘッダとの不一致を同じ翻訳単位で検出できます．別ファイル同士の型の不一致を，リンカが必ず発見してくれると考えてはいけません．

### 3.2　インクルードガードの読み方

1. `#ifndef PL1_CALC_H`で，まだこのマクロが定義されていないかを調べる．
2. 初回は`#define PL1_CALC_H`で印を付け，宣言を取り込む．
3. 同じ翻訳単位で再び読まれたら，印があるので`#endif`までを飛ばす．

同じ関数プロトタイプを複数回宣言するだけなら問題にならない場合もあります．しかし，同じ構造体の定義が重ねて現れるとエラーになります．内容が今は関数宣言だけでも，ヘッダには最初からガードを付けておきます．

ガード名はヘッダごとに異なる名前にします．すべてを`HEADER_H`にすると，別のヘッダまで読み飛ばす原因になります．先頭がアンダースコアと大文字の名前など，処理系のために予約された名前を避け，ここでは`PL1_`で始めます．

MSVCでは`#pragma once`も使えますが，これはISO C17の標準機能ではありません．本資料では標準的な条件付き前処理を用いたガードを使います．ガードの効果は**その翻訳単位の中だけ**であり，異なる`.c`へ同じ関数本体を書く問題を解決しません．

## 4　Visual Studioで分割する {#split}

1. 空のC++プロジェクト`SplitCalc`を作り，C17・Cとしてコンパイルを設定する．
2. 同じプロジェクトフォルダに上の3ファイルを保存する．
3. `main.c`と`calc.c`を「ソース ファイル」に，`calc.h`を「ヘッダー ファイル」に追加する．
4. Ctrl+Shift+Bでビルドし，Ctrl+F5で実行する．

この回は**1つの`main`と複数の`.c`**を同じプロジェクトに入れます．拡張子は`.cpp`ではなく`.c`です．ソリューションエクスプローラーの「ソース ファイル」等は分類用フィルターなので，実際のフォルダと同一とは限りません．

| 症状 | 調べること |
| --- | --- |
| ヘッダが見つからない | ファイルの保存場所とインクルード検索パス |
| 宣言がない・型が違う | ヘッダの宣言とインクルード |
| 外部シンボルが未解決 | 実装の`.c`がプロジェクトに含まれ，ビルド対象か |
| シンボルが重複 | 関数本体や`main`を2か所で定義していないか |

### 4.1　プロジェクトと実ファイル

フォルダへファイルをコピーしただけでは，プロジェクトのビルド対象に入らない場合があります．「追加 → 既存の項目」で`.c`を登録し，「ビルドから除外」が「いいえ」になっていることを確かめます．ヘッダはそれ自体を通常の`.c`のようにコンパイルするものではありません．ソリューションエクスプローラーへの登録は管理上便利ですが，取り込みには実際のファイルの場所が重要です．

ファイルが増えたときの配置例です．学習用の小さなプロジェクトでは，同じフォルダに置いてもかまいません．

~~~text
SplitCalc/
  include/  calc.h             公開する宣言
  src/      main.c, calc.c     自分で編集する実装
  lib/      配布された.lib    リンク用の入力
  bin/      .exeや必要な.dll   実行時に使うもの
  build/    .objなど           作り直せる中間生成物
~~~

これは役割を表す例で，Visual Studioが必ずこの配置で出力するという意味ではありません．実際の中間ディレクトリと出力ディレクトリはプロジェクト設定で確認します．`.c`や`.h`を消しても`.obj`から元のコメントや変数名をすべて復元できるわけではないので，ソースを必ず保存します．

### 4.2　発展：前処理後の内容を見る

Visual Studioのファイルのプロパティで「C/C++ → プリプロセッサ → プリプロセス済みファイルの生成」を有効にすると，`/P`によって`.i`を生成できます．`.c`を選んで「コンパイル」すると，ヘッダを取り込んだ内容や，元の行位置を表す`#line`を確認できます．表示名はバージョンや言語設定で多少異なります．

**確認後は必ず設定を元に戻し，リビルドしてください．** `/P`は前処理だけを行い，`.obj`を作りません．設定したままでは通常のコンパイルが進みません．[Microsoft：/Pの説明](https://learn.microsoft.com/en-us/cpp/build/reference/p-preprocess-to-a-file?view=msvc-170)も参照してください．

## 5　ライブラリ

よく使う関数群をまとめて再利用するものがライブラリです．Windowsでは静的ライブラリに`.lib`，動的ライブラリに`.dll`が使われます．ただし`.lib`はDLL用のインポートライブラリの場合もあります．拡張子だけで実装をすべて含むとは判断できません．

| 種類 | 主に結び付ける時期 | 利用時の注意 |
| --- | --- | --- |
| 静的ライブラリ | ビルド時 | 必要なコードが実行ファイルに組み込まれる．更新後は再リンク |
| 動的ライブラリ | 読み込み時・実行時 | 対応するDLLの配置と互換性が必要 |

ヘッダがあるだけでは実装は使えません．逆にライブラリがあっても，呼び出し側は正しい宣言を知る必要があります．標準ライブラリには`stdio.h`，`string.h`，`math.h`などのヘッダがあります．Windows/MSVCでは`Unix`向けの`-lm`を入力する手順は用いません．

### 発展：静的ライブラリに分ける

Visual Studioでは，空のプロジェクトの構成の種類を「スタティック ライブラリ（`.lib`）」にして`calc.c`をビルドし，別のアプリから参照できます．アプリとライブラリでx64等のプラットフォームと構成をそろえます．演習に手順を示します．[Microsoftの静的ライブラリの説明](https://learn.microsoft.com/en-us/cpp/build/walkthrough-creating-and-using-a-static-library-cpp?view=msvc-170)も参考になります（掲載例はC++ですが，本演習のソースはCです）．

## 6　公開するものを限定する

`.c`のファイルスコープで `static` を付けた関数は，その翻訳単位内で使う内部の関数にできます．共有変数を使うならヘッダには `extern int count;` と宣言し，定義 `int count = 0;` は1つの`.c`だけに置きます．ただし，できるだけ引数と戻り値で情報を渡し，共有状態を減らします．

### 6.1　`static`と`extern`

~~~c
/* counter.hに書く宣言の例 */
extern int count;
void increment(void);
~~~

~~~c
/* counter.cに書く定義の例 */
int count = 0;

void increment(void)
{
    ++count;
}
~~~

実際の`counter.c`も`counter.h`を取り込みます．`extern int count;`は「他に定義がある」ことを知らせる宣言で，初期化子のないこの形では変数の領域を定義しません．一方，ヘッダに`int count = 0;`を書くと，各`.c`が同じ変数を定義してしまいます．

外に公開しない状態なら，`.c`のファイルスコープに`static int count = 0;`と置き，読み書きする関数だけを公開する設計もできます．ここでの`static`は名前を他の翻訳単位から直接参照させない指定です．関数内の`static`変数が呼び出しをまたいで値を保持する話と，区別して整理してください．

内部の比較関数なども，`static int compare_int(...)`のようにして公開する名前を減らせます．ヘッダには利用者が必要とする操作だけを並べます．内部の関数を変更しても，公開する使い方が変わらなければ利用者側の修正を減らせます．

## 7　構造体を含むモジュール：ベクトルと行列

2成分の`Vector`と2行2列の`Matrix`を考えます．第11回と同じく構造体の値を受け渡しますが，計算を`vector.c`と`matrix.c`へ分けます．この例は`Calc`とは**別のプロジェクト**です．

### 7.1　型の依存関係

~~~text
vector_main.c ──→ matrix.h ──→ vector.h
       └────────────────────→ vector.h
matrix.c      ──→ matrix.h ──→ vector.h
vector.c      ──→ vector.h
~~~

`matrix.h`に宣言する関数は`Vector`を引数と戻り値に使うので，`matrix.h`自身が`vector.h`を取り込みます．利用者に「先に必ず`vector.h`を読んでください」と要求するより，**ヘッダが自分で必要な宣言を読み込む**方が安全です．`vector_main.c`からは`vector.h`へ2通りの経路がありますが，ガードによって重複を防げます．

~~~c title="vector.h" linenums="1"
--8<-- "sample/12/vector.h"
~~~

~~~c title="matrix.h" linenums="1"
--8<-- "sample/12/matrix.h"
~~~

`Vector`の`v`は2要素の配列，`Matrix`の`v`は4要素の配列です．行列は行ごとに並べ，`v[0]`と`v[1]`が第1行，`v[2]`と`v[3]`が第2行です．行番号`i`，列番号`j`を0から数えると，対応する添字は`2 * i + j`です．

### 7.2　計算の実装

`axpy(alpha, a, b)`は，ベクトルの各成分で`alpha * a + b`を計算します．ここでは入力を値渡しにし，新しい`Vector`を返すため，呼び出し側の`a`や`b`は変更しません．

~~~c title="vector.c" linenums="1"

~~~

`gemv(alpha, a, x, beta, y)`は`alpha * A * x + beta * y`です．行列とベクトルの積`Ax`では，第1成分に第1行と`x`の積の和，第2成分に第2行と`x`の積の和を使います．

~~~c title="matrix.c" linenums="1"

~~~

~~~c title="vector_main.c" linenums="1"
--8<-- "sample/12/vector_main.c"
~~~

[`vector.h`](sample/12/vector.h){ download } ／ [`matrix.h`](sample/12/matrix.h){ download } ／ [`vector.c`](sample/12/vector.c){ download } ／ [`matrix.c`](sample/12/matrix.c){ download } ／ [`vector_main.c`](sample/12/vector_main.c){ download }

このプロジェクトでコンパイルするのは`vector_main.c`，`vector.c`，`matrix.c`の3つです．実行すると次のようになります．

~~~text
[1.0 -1.0]
[-1.0 1.0]
(5.0, 8.0)
(1.0, 6.0)
~~~

`2x + y = (2×1+3, 2×2+4) = (5, 8)`です．一方，`Ax = (1−2, −1+2) = (−1, 1)`なので，`2Ax + y = (1, 6)`になります．ファイル分割の前に手計算し，分割後も同じ計算になっていることを確かめましょう．

### 7.3　発展：内部の構造を隠す

上のヘッダではメンバを公開しているため，利用者が`x.v[0]`と直接書けます．内部を配列から別の表現へ変更すると，利用者のコードも修正が必要です．もう一段進むと，ヘッダでは次のように名前だけを知らせる方法があります．**これは上の完成例とは別の設計案です．そのまま置き換えません．**

~~~c
typedef struct vector Vector;
double get_vec_element(const Vector *p, int index);
~~~

`struct vector`の中身を示していないので，この段階では不完全型です．利用者は`Vector *`を扱えますが，`Vector x;`で実体を用意したり，`sizeof(Vector)`を調べたり，メンバを直接参照したりはできません．実装の`.c`の中で`struct vector { double v[2]; };`と定義し，必要な操作を関数で提供します．

実体をライブラリ側で動的に作る場合には，作成関数，失敗を知らせる方法，解放関数をそろえます．例えば解放関数を`void destroy_vector(Vector **p);`とすれば，解放後に呼び出し元のポインタを`NULL`にする設計ができます．ただし，他のポインタに複製された参照まで自動的に`NULL`になるわけではありません．この実装は，第13回の`malloc`・`free`と所有権を学んでから扱います．

添字を渡す取得関数では0〜1などの範囲の契約も必要です．無理なキャストで内部をのぞくのではなく，公開された操作を使います．内部を隠すことと，入力検査・寿命管理が不要になることは別です．

## 8　標準ライブラリを使い分ける

自作のライブラリと同様に，標準ライブラリも「宣言を読み，決められた条件で呼び出す」ものです．ヘッダを1つ読めばすべての関数が宣言されるわけではありません．使用する機能に対応したヘッダを取り込みます．

| ヘッダ | 主な内容 | 使うときの確認 |
| --- | --- | --- |
| `math.h` | `cos`，`exp`，`pow`，`sqrt`，`fabs`など | 引数の範囲，浮動小数点誤差 |
| `limits.h` `/` `float.h` | `INT_MAX`，`FLT_MAX`など | 大きさ，範囲，精度は型・処理系ごとに異なる |
| `ctype.h` | `isalpha`，`isdigit`など | 引数が`EOF`または`unsigned char`で表せる値か |
| `string.h` | `strcpy`，`memcpy`，`memcmp`など | 終端，容量，バイト数，領域の重なり |
| `assert.h` | `assert`マクロ | 開発中の前提確認であり，入力検査の代わりではない |
| `stdlib.h` | `strtol`，`qsort`，`rand`，`srand`など | 変換失敗，比較関数の契約，乱数の性質 |

### 8.1　数学関数と型の限界

`sqrt(9.0)`は3，`pow(3.0, 2.0)`は9，`fabs(-2.5)`は2.5を計算します．`cos`の角度はラジアンです．`exp(x)`は自然対数の底`e`の`x`乗です．`sqrt`に負の値を渡すなど，数学的に定義されない入力を避け，範囲が不明なら先に検査します．計算結果には丸め誤差があるため，厳密な実数と同じだとは考えません．

円周率の`M_PI`はISO C17の標準マクロではありません．この授業では必要なら`acos(-1.0)`を使うか，必要な精度の定数を自分で定義します．環境固有のマクロが別の処理系でも使えると思い込まないようにします．

`INT_MIN`と`INT_MAX`は`int`の範囲を表します．一方，**`FLT_MIN`は`float`の最も負の値ではなく，最小の正の正規化数**です．負の側の有限値の限界は通常`-FLT_MAX`で表します．`FLT_TRUE_MIN`は非正規化数を含む最小の正の値です．範囲を表すマクロと，精度を表す`FLT_DIG`などは意味が違います．

### 8.2　文字の判定とバイト列のコピー

`isalpha`や`isdigit`は，条件に合えば0以外を返します．「真なら必ず1」ではありません．真偽を0または1で表示したいなら`isdigit((unsigned char)c) != 0`とします．`char`が符号付きの環境で負の値をそのまま渡さないようにします．`getchar`の結果を`int`で保持した場合は`EOF`と区別できます．

次の2つの操作は，途中に終端文字があるデータで違いが分かります．

~~~c
char src[5] = {'a', 'b', '\0', 'c', 'd'};
char text[10] = {0};
char bytes[10] = {0};
/* string.hを取り込んだ関数内で行う操作の例 */
strcpy(text, src);
memcpy(bytes, src, sizeof src);
~~~

`strcpy`は最初の`'\0'`までを，その終端も含めてコピーします．`memcpy`は指定された5バイトをそのままコピーするので，`c`と`d`もコピーされます．この例のコピー先は十分な容量を持ち，重なっていません．一般の入力でも安全という意味ではありません．MSVCで`strcpy`に警告が出る場合も，単に警告を消すのではなく容量の根拠を確認します．

`memcpy`は文字列の終端を補いません．コピー先・元の範囲を確保し，領域が重なる場合には`memmove`を検討します．ポインタをコピーしても参照先までは複製しません．構造体の`memcmp`も，パディングがあるため値の等価判定としては使えないことを第11回と結び付けましょう．

### 8.3　`assert`による前提の確認

`assert`は関数ではなくマクロで，式が偽なら診断を出して異常終了します．開発時に「ここに来たらこの条件が成立するはず」を確認するものです．

~~~c
/* assert.hを取り込んだ関数内．nは検査済みの個数 */
assert(n >= 0 && n <= capacity);
~~~

`NDEBUG`が定義されていると`assert`は無効になります．そのため，ユーザーの入力やファイルの内容は`if`などで常に検査します．`assert(++n < capacity);`のように副作用を入れると，設定によって`n`を増やす処理自体がなくなるので不適切です．`assert`が正常に通っただけで，すべての入力に正しいと保証されたわけでもありません．

### 8.4　擬似乱数と並べ替え

`rand`は0〜`RAND_MAX`の整数を返します．`srand`で種を与え，同じ処理系で同じ種から始めれば同じ系列を再現できます．系列そのものは処理系に依存するので，他の環境と数値が一致するとは限りません．種は通常ループの前に一度設定します．

`(double)rand() / RAND_MAX`は0と1の両端を含み得ます．`rand() % 10`は0〜9になりますが，取り得る元の値の個数が10で割り切れなければ偏りがあります．`rand`は暗号やパスワード生成のための乱数ではありません．

`qsort`は配列を並べ替えます．要素の先頭アドレス，個数，1要素のサイズ，比較関数を渡します．比較関数は2つの要素を受け取り，第1要素が小さければ負，等しければ0，大きければ正を返します．`int`同士でも`a - b`を返すとオーバーフローし得るため，大小比較から−1・0・1を選びます．演習ではこの比較処理を内部関数にし，並べ替え操作だけを公開します．

`stdlib.h`には外部コマンドを実行する`system`もあります．これは文字列からOS側の処理を起動する機能であり，未確認の入力を渡すと意図しないコマンドを実行する危険があります．この授業では存在と役割の説明にとどめ，実行する演習は行いません．

## 9　ライブラリ利用の設定を整理する

「ヘッダが見つからない」と「関数の実装が見つからない」を区別するため，設定を段階に分けます．

| 必要なもの | Visual Studioで確認する場所の例 | 役割 |
| --- | --- | --- |
| `.h`の検索先 | C/C++ → 全般 → 追加のインクルード ディレクトリ | 宣言を読む |
| `.lib`の検索先 | リンカー → 全般 → 追加のライブラリ ディレクトリ | 指定された`.lib`を探す |
| 使う`.lib`の名前 | リンカー → 入力 → 追加の依存ファイル | 実際にリンクする対象を指定する |
| 同じソリューション内のライブラリ | 利用側のプロジェクト参照 | 依存先のビルドやリンクを連携させる |
| 実行時のDLL | 配布元の指示に従った配置・検索先 | ロード時・実行時に実装を利用する |

検索フォルダだけを設定しても，その中のすべてのライブラリが自動的に使われるわけではありません．逆に，`.lib`の場所を直接指定する方法なら検索先を別途追加しなくてもよい場合があります．同じソリューション内の参照と，配布済み`.lib`を名前で指定する方法を混同しないようにします．

静的ライブラリはオブジェクトをまとめたもので，作成時にアプリ用の`main`は必要ありません．Windowsの`.lib`に対し，他の環境では`.a`がよく使われます．共有ライブラリも`.dll`のほか`.so`などの名称があります．他の環境向けのビルド操作をそのまま入力する必要はありません．

静的ライブラリの実装を更新したら，利用側を再リンクして更新分を取り込みます．DLLは互換性の保たれた更新ならアプリを再リンクせず交換できる場合がありますが，引数の型，構造体の配置，呼び出し規約などが変われば単純な交換では済みません．x86/x64や実行時ライブラリの設定もそろえます．不明な配布元から同名のDLLを探して置く方法で解決しないでください．


## 確認問題

1. ヘッダのインクルードはリンクと同じ処理か．
2. インクルードガードは何の重複を防ぐか．
3. 宣言が正しくてもリンクで失敗する例を挙げよ．
4. `calc.c`の本体の変更と`calc.h`の宣言の変更では，再コンパイルが必要な範囲はどう違うか．
5. `matrix.h`が`vector.h`を自分で取り込む理由を説明せよ．
6. `extern`宣言をヘッダに置くことと，初期値付きの変数定義を置くことはどう違うか．
7. 静的ライブラリを更新したとき，すでに作った`.exe`の内容も自動的に変わるか．
8. `FLT_MIN`，`isdigit`の戻り値，`assert`について，間違えやすい点を1つずつ挙げよ．

??? note "確認の要点"

    `include`は宣言などの取り込み，リンクは定義との結び付けです．ガードは同一翻訳単位内でのヘッダの再取り込みを抑えます．実装を除外すれば，宣言が正しくてもリンクに失敗します．ヘッダの変更はそれを読む各翻訳単位へ波及します．型の依存先をヘッダ自身で取り込むと，読み込む順序に依存しにくくなります．`extern`による宣言と領域を与える定義は区別し，静的ライブラリの更新は再リンクして取り込みます．`FLT_MIN`は正の値，文字判定の真は非0，`assert`は設定で無効になり得る，という点も確認してください．
